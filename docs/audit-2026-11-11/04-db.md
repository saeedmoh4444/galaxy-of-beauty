## 2. Gaps 🔴

1. **Seed is not idempotent — second run fails.** `prisma/seed.ts:17-136` cleanup deletes neither `storeCheckout` nor `storeOrder` rows, yet the seed creates them (`seed.ts:3850-3884`). `vendor.deleteMany()` cascades `store_orders` (baseline migration.sql:4789 CASCADE), but `store_checkouts.customerId` is ON DELETE RESTRICT (`20261003000000_fatoorah_checkout/migration.sql:42`), so `db.user.deleteMany()` at `seed.ts:134` aborts with an FK violation on a re-seed. Severity: HIGH. Fix: add `storeCheckout.deleteMany()` (after orders) to the cleanup transaction. Effort S.
2. **StoreCheckout webhook + expiry queries are unindexed seq-scans.** Fatoorah callback lookup `storeCheckout.findFirst({ where: { OR: [{ invoiceId }, { gatewayRef }] } })` (`packages/api/src/routers/payments.ts:909`) and the 15-min expiry sweep `findMany({ where: { status: 'PENDING', createdAt: { lt } } })` (`packages/api/src/workers/checkoutExpiry.ts:17`) — none of `invoiceId`/`gatewayRef`/`status` are indexed (`schema.prisma:2076-2078`; only `@@index([customerId, createdAt])` at :2092). Severity: MEDIUM perf, grows linearly with checkout table. Fix: `CREATE INDEX ON store_checkouts(status, createdAt)` + partial unique on gatewayRef/invoiceId. Effort S.
3. **No FK on money-adjacent tables.** `GiftCard.purchaserId` (schema.prisma:2187), `GiftCardTransaction.giftCardId` + `bookingId` (schema.prisma:2204-2205), `FlashDealClaim.userId` (schema.prisma:3244) have indexes/uniques but no FK relation in schema and no FK in any migration (verified against full FK list). Orphan financial rows possible. Severity: HIGH. Fix: add relations + migration FKs (dedupe orphans first). Effort S-M.
4. **Referral double-claim.** `Referral` has no `@@unique([referrerId, referredId])` (schema.prisma:1272-1296, only 3 plain indexes) and `referrals.ts:211` creates without any prior-existence check → same user can apply a code repeatedly for multiple rewards. Severity: HIGH. Fix: compound unique + upsert-style guard. Effort S.
5. **Booking slots have no DB-level overlap guard.** `AvailabilitySlot` lacks a unique on `(technicianId, startAt, endAt)` (schema.prisma:667-684) — double-booking under concurrency is app-logic only. Severity: MEDIUM. Fix: exclusion constraint or unique on (technicianId, startAt). Effort M.
6. **Unique-but-unconstrained owner ids on core rows.** No FK from: `beauty_profiles.userId` (schema.prisma:2370), `customer_ai_subscriptions.userId` (:1099), `customer_quiz_responses.userId` (:1154), `bridal_concierges.userId` (:2402), `group_bookings.organizerId` (:2217), `family_members.userId` (:3258), `event_registrations.eventId/userId` (:2651-2652), `technician_badge_assignments.technicianId` (:2447), `shorts.technicianId` (:2715), `flash_deals.serviceId` (:3220), `bnpl_plans.userId` (:4769), `recommendation_feedback.userId` (:1164), `beauty_circles.creatorId` (:3903), `home_service_requests` (all ids, :2677-2686), `vip_memberships`/`salon_memberships`/`she_leads_members`/`beauty_integrations`. Unique indexes exist (baseline: e.g. `beauty_profiles_userId_key` migration.sql:4084) but no FK constraint — orphans can be created by any client write. Severity: MEDIUM (integrity posture). Fix: one migration adding FKs after orphan cleanup. Effort M.
7. **Dispute dual-target without CHECK.** `bookingId` and `storeOrderId` both nullable (schema.prisma:882-883), no constraint that exactly one is set; rows with both null or both set are writable. Severity: MEDIUM. Fix: `CHECK (num_nonnulls(bookingId, storeOrderId) = 1)`. Effort S.
8. **PromoUsage single-use hole.** `@@unique([promoCodeId, userId, bookingId])` with nullable `bookingId` (schema.prisma:1435) — Postgres treats NULLs as distinct, so non-booking redemptions are unlimited. The app guard (`promo.ts:105-113`) covers booking redemptions only; store-checkout promos would be exposed (checkout currently applies no promos — latent). Severity: MEDIUM latent. Fix: partial unique index `WHERE bookingId IS NULL`. Effort S.
9. **Duplicate model families — divergent pricing/rating logic.** `ServicePricing` (schema.prisma:557) vs `PricingRule` (:3816) — two dynamic-pricing tables; `ServiceBundle` (:581) vs `BeautyBundle`+`BundleService` (:3835,:3861) — two bundle systems; `PromoCode` (:1396) vs `BeautyCoupon` (:4698) — two coupon systems; `Review` (:860) vs `TechnicianRating` (:4636, also has bookingId @unique) — two rating systems that can double-count. All four pairs are live tables. Severity: MEDIUM (logic), HIGH (audit risk). Fix: deprecate/backfill-merge the legacy copies. Effort L.
10. **StoreOrder lacks an order code.** Every other order-like entity has one (`bookingCode` GOB-, GymClassBooking GYM-, TrainerSession TRN-, NailBarBooking GON-, ClinicConsultation GOC-) but `StoreOrder` (schema.prisma:2014-2038) is id-only — no support/merchant reference, no idempotency handle. Severity: LOW. Effort S.
11. **Payout settlement query not fully covered.** Daily job `storePayouts.ts:32-34` filters `vendorId NOT NULL + status COMPLETED + createdAt range`; existing indexes are `(vendorId)` and `(status, createdAt)` (schema.prisma:749-753) — bitmap merge each run. Fix: `(vendorId, status, createdAt)`. Effort S.
12. **`product.sales` sort unindexed.** `vendorPortal.ts:369` `orderBy: { sales: 'desc' }` (and lifeStage.ts:45) — no index on `sales`. MEDIUM for large catalogs. Effort S.

## 5. Best-practice assessment

**Migration discipline — good.** 49 migrations, strictly chronological `YYYYMMDDHHMMSS` names, `migration_lock.toml` present, no duplicate names, all schema models have tables (baseline + incrementals verified). The `ALTER TYPE ... ADD VALUE` hazard is handled correctly 4 times (each addition in its own migration file, never used in the same transaction — e.g. `20261110000000_seller_role_enum` + `...00100_seller_role_backfill`, which is also codified as a contract test in `src/seller-role.test.ts`). Hand-written SQL is clearly commented and mostly additive. Weaknesses: one hand-written migration adds redundant indexes (§3.2), and one known merge-conflict brace lives on in seed.ts (§3.1).

**Seed strategy — good with one blocker.** seed.ts is E2E-first: admin/customer/9 technicians, SELLER demo store + 3 per-project payouts + staff + per-project invitees (concurrency-aware for chromium/firefox/mobile-chrome), paid checkouts + orders with line items, Beauty DNA products, flash deals, promos, subscriptions, 289-item women's catalog mapping, shorts + shoppable tags — everything the 39 web specs and 3 mobile specs reference is seeded. The re-run FK failure (§2.1) and the misplaced moderation fixture (§3.1) are the two real defects; enrich script exists for scale testing.

**Data-integrity posture — mixed, leaning weak.** Strong: uniques on natural keys (email, phone, bookingCode, storeSlug, idempotencyKeys), compound uniques on join tables, snapshot columns on order items, `onDelete: Restrict` defaults on money rows (store_orders/store_checkouts → users), ZATCA hash chain with cascade discipline. Weak: a large class of owner ids are indexed-but-unconstrained (no FK) including money-adjacent gift-card tables (§2.3, §2.6), duplicate model families can produce inconsistent pricing/rating reads (§2.9), no CHECK constraints anywhere (Prisma 7 schema can't express them — DB-side), and nullable-compound-unique holes (§2.8, §3.11). Prisma 7 adoption is correct (prisma.config.ts, driver adapter, `$on('query')` replacing removed `$use`, no relationMode override → FK mode confirmed in DDL); no deprecation warnings found in schema or docs. db package tests are thin (client.test.ts lazy-init checks + seller-role file-contract test) — no integration tests against a real DB in the package itself; the API package's `__tests__` carry that load.
