## 2. Gaps 🔴

1. **Booking picker truncated to 100 newest rows — the 75 core (technician-bearing) services are unreachable.** `services.list({page:1, limit:100})` with default `newest` sort (web `apps/web/src/app/(customer)/bookings/create/page.tsx:70`; mobile `apps/mobile/src/app/customer/bookings/create/index.tsx:151`, `MAX_LIST_SIZE=100` in `packages/shared/src/constants.ts:33`). The 289 D2 rows are created last in seed → they fill the picker; the seeded core services fall off. Combined with gap 2, every picker option fails. Fix: paginate/search the picker, or exclude `womens-services` rows from the booking picker. Effort S.
2. **~90% of catalog unbookable — no technician mapping.** seed.ts:2576-2583 (1 random service/tech) + E1/babysitting/D2 services created outside the assignment array (seed.ts:1251-1254, 1316, 4680). Every D2, kids, babysitting, fitness, barberette, postpartum, hijab service books nowhere. Fix: seed a real tech roster per category (or a platform pool technician per category like the store pseudo-tech pattern). Effort M.
3. **Booking confirm shows placeholder code/date.** Web `router.push('/bookings/confirm')` passes no params (create/page.tsx:199); confirm reads `params.get('code') || '———'` (confirm/page.tsx:17-19). Mobile identical (create/index.tsx:258; confirm/index.tsx:14-16). Fix: pass `?code=&date=` from the mutation result. Effort S.
4. **Booking → payment path missing on both platforms.** `payments.authorize` exists and is correct (payments.ts:116-214, ACCEPTED precondition, MyFatoorah LNK + cash) but **zero call sites in apps/web or apps/mobile** (grep). Web booking detail has no pay CTA and a **no-op cancel button** (`onClick={() => {}}` at `apps/web/src/app/(customer)/bookings/[id]/page.tsx:128-133`; mobile cancel IS wired via `bookings.transition`, `[id]/index.tsx:48-135`). Bookings are stuck at REQUESTED/ACCEPTED. Fix: pay/cancel actions on booking detail (web parity with mobile). Effort M.
5. **Flash-deal price never reaches a booking total.** No flashDeal logic in bookings.ts (grep: 0 hits); `flashDeals.claim` only increments redemptions and returns the price (flashDeals.ts:84-122); web "Book now" just claims (FlashDealsClient.tsx:251-257) and the service link books at full basePrice. Fix: pass `dealId` through create → apply `dealPrice` + validate claim ownership. Effort M.
6. **No women-only privacy gate anywhere.** `trpc.ts` has role-based procedures only (lines 141-230); no gender/women-only middleware. Enforcement = hiding mens-grooming (services.ts:45, categories.ts:34) + display-only badges (`isWomenOnlyStaff` is a filter flag, services.ts:48). Worse: mobile `public/services` uses `categories.tree`, which does **not** filter mens-grooming (categories.ts:50-54) → men's-grooming chip renders on mobile browse (selecting it returns empty because of the contradiction with services.ts:40+45). Fix: add a tree filter + decide whether a real gate is required (it is, if "women-only" is a compliance claim). Effort M.
7. **bookings.create validates neither technician↔service mapping nor address ownership.** Technician lookup is existence-only (bookings.ts:129-137); `addressId` is written straight through (bookings.ts:452). A crafted request books any technician for any service and attaches another user's address (which the technician then sees). Fix: verify `TechnicianService` link + `address.userId === ctx.user.id`. Effort S.
8. **Mobile catalog is broken in three places.** (a) `apps/mobile/src/app/public/services/index.tsx:93-106` renders `s.nameAr/descAr/price/duration` — fields the API doesn't return (payload is `titleJson/basePrice/durationMin`) → blank cards, and cards are plain Views with no navigation to `/services/[id]`. (b) mobile womens-services (index.tsx:63-71) and kids-services (index.tsx:64-74) map `selectedCat.services`, but `womensServices.categories`/`kidsServices.categories` return `serviceCount` only (womensServices.ts:12-20, kidsServices.ts:189-197) → tapping any category renders an empty section; no booking anywhere on mobile (web has full booking wizards on both pages: `(public)/womens-services/page.tsx:45-56`, `(public)/kids-services/page.tsx:40-47`). Fix: align payloads/UI, add book flow. Effort M.
9. **womensServices.book / kidsServices.book assign "first technician by id" with no slot, no mapping check, static pricing.** womensServices.ts:103-110, 124; kidsServices.ts:266-273, 286 — booking created against a technician who likely doesn't offer the service, with no AvailabilitySlot, no dynamic pricing, no flash deal. Also kidsServices.book never attaches `familyMemberId` despite K1 shipping. Fix: reuse the main create validation or at minimum the technician↔service check. Effort M.

## 3. Errors 🟡

1. **Cache invalidation is dead code.** `invalidateCachePrefix` sits _after_ `return` in services.ts create/update/delete (services.ts:476-477, 522-523, 549-552) — unreachable; admin service edits leave browse stale up to the 5-min TTL (cache.ts:5). categories.ts does it correctly before returning (categories.ts:141-144).
2. **womensServicesMap fallbacks resolve to the wrong (or no) service.** `WOMENS_FALLBACK_SERVICE = 'Beauty Consultation'` (womensServicesMap.ts:97) exists in seed only as the **kids-care** row `teen-beauty-consultation` (seed.ts:1232) — fallback women's bookings land on a kids service. Keyword targets like `'Hair Color'`, `'Facial Cleansing'` (womensServicesMap.ts:70, 76) don't exactly match any seeded `titleJson.en` (`'Full Hair Color'`, `'Deep Facial Cleansing'`) → `resolveWomensServiceId` returns 0 → NOT_FOUND. Latent only while all 289 mapping rows are seeded; breaks on any missing mapping.
3. **Duplicate catalog names across the two catalogs.** Kids facade rows duplicate core names ('Manicure' kids-girls-manicure seed.ts:1225 vs 'Gel Manicure'; 'First Haircut' seed.ts:1218 vs 'First Haircut Package' seed.ts:1156), and the 289 D2 rows share the general browse with the core catalog (services.list has no category exclusion for `womens-services`) — browse is flooded by the facade catalog. The `womens-services` category is upserted without iconUrl/sortOrder (seed.ts:4685-4692) so it renders as the **first** chip on the web browse with a missing icon.
4. **seed-enrich bookings ignore the TechnicianService mapping.** seed-enrich.ts:353-355 picks technician and service independently — analytics bookings exist on services the technician never offered.
5. **Dynamic pricing shipped but dormant.** Engine is clean (`lib/pricing.ts`), wired into bookings.create (bookings.ts:300-336) and `pricing.preview` (pricing.ts:33-82) with admin CRUD (pricingAdmin.ts) + admin UI (`apps/web/src/app/admin/pricing/page.tsx`), but **no seeded service has `dynamicPricingEnabled`** (seed.ts:2613-2615 comment; default false) → peak/surge never fire without admin opt-in; `smartPricing` router is a deliberate fail-closed stub (smartPricing.ts:9-20).
6. **Service images: 0/393 rows have `imageUrl`.** All service create blocks omit it; seed-demo-full.ts:177 explicitly null. Category-fallback stock imagery only (web ServiceDetailClient.tsx:130-138). E2 image pipeline remains user-gated (AUDIT_2026-10-30-full.md:138).
7. **Web booking detail cancel button is inert** (`bookings/[id]/page.tsx:130`, `onClick={() => {}}`) while the API supports it — parity bug vs mobile.

## 5. Best-practice assessment

- **Data modeling: strong.** Bilingual `titleJson`/`nameJson`, flag-driven trust/stage dimensions (isWomenOnlyStaff/isPregnancySafe/isMommyFriendly/isHourly), booking-time snapshots (`pricingBreakdown`, `addonsJson`, `beautyBundleJson`), idempotency keys, state machine with explicit transitions (bookings.ts:34-63). The seed strategy is the weak point: random technician-service assignment leaves the catalog mostly unbookable and produces two parallel catalogs with no dedup.
- **Pricing design: sound where wired.** Opt-in engine with multiplicative tier/peak/surge, preview mirroring create (pricing.ts:1-84), snapshot persisted on the booking. Undermined by: nothing opted in (dormant), flash-deal prices never applied, hourly pricing correct on server but UI previews from durationMin rather than the selected window.
- **Privacy posture: honest assessment — it is a marketing posture, not an enforcement.** The only real controls are the mens-grooming exclusion and auth-scoped customer procedures; there is no gender gate, no verified-female KYC step, address ownership is unchecked on create, and every catalog read is public. On a Saudi women-only platform claim, the highest-value fix is not more badges but the address-ownership check + a gender/eligibility gate on registration/booking, plus the mobile tree leak.
- **Booking engine core is solid** (idempotency, slot re-check in transaction, jummah windows, bundle/addon/subscription math) — the customer-facing completion (payment entry, confirm data, technician/slot selection) is where the flow falls apart.
